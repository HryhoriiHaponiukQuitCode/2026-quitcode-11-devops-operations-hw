# Трек розробника WS11: покроково

Ви продовжуєте **своє репо** `<я>/<team-slug>` з WS6–WS10: той самий Supabase, той самий Vercel, ruleset `solo-main`,
ворота, smoke і `/api/health` з WS8. Нового репо немає. Цього тижня продукт стає **експлуатованим**: зміна йде на прод
через перевірене середовище, про збій першою дізнається людина з команди, а інцидент — це процедура, а не паніка:

- **A** — середовища й реліз: гілка `staging` зі змінною лише для неї, smoke кожного деплою з обходом захисту, доступ
  PM до staging, тег `v1.0.0` після приймання PM;
- **B** — сигнали: алерт людині з червоного smoke, трекер помилок сервера, журнал AI-функції `llm.call` без тексту
  користувача;
- **C** — інцидент-дріл на staging: зламати → помітити сигналом → розбір агентом у профілі «лише пропонує» →
  виправити → postmortem → runbook → нова перевірка в CI;
- **D** — ланцюг постачання: Dependabot з паузою, `.npmrc` з `min-release-age`, дії за SHA, push protection і CodeQL,
  `next` ≥ 16.4.5.

Бонус (необов'язково) — зашифрована копія бази з тренуванням відновлення або асистент чергового лише на читання.

Корисні посилання:

- Рубрика й Definition of Done — у [README](../README.md#трек-розробника--100--10-балів).
- **Промпти агенту для кожного кроку** — [бібліотека промптів WS11](prompts.md) (R01–R18; R19–R21 — необов'язкові,

  блоці «Для домашки WS11» під кожним промптом:** скопіюйте промпт і заповніть слоти звідти.

  покласти, які секрети потрібні й як перевірити. Таблиця «що куди» — у [`materials/README.md`](../materials/README.md).
- **Гайди:** [середовища, реліз і ланцюг постачання](release-guide.md) · [сигнали](signals-guide.md) ·

**Кожна задача — окремою гілкою й PR, як у WS7–WS10:** зелений CI і `quality` → `@coderabbitai review` окремим
коментарем → **відповідь на кожну знахідку рецензента** (виправлення або аргумент у треді) → Squash and merge. Взяли
файл з `materials/` — в описі PR «взято з <посилання на файл>».

**Чого не робимо ніколи:** не відкриваємо `.env*` у чаті з агентом і не вставляємо туди значення секретів; не
запускаємо `supabase migration down` і `db reset --linked` проти свого проєкту; не беремо `npx supabase@latest` (лише
закріплена версія з проєкту); не даємо агенту права запису на проді; не ламаємо прод і базу заради дрілу.

## 1. Підготовка, аудит і ланцюг постачання (~1 год) — D0, трек D

Навіщо: Dependabot, `.npmrc` і закріплені дії — три замки на вході залежностей. Ви не пишете Next.js чи
`actions/checkout`, але відповідаєте за все, що вони роблять у вашому CI і на проді. Чому саме так — у
[release-guide, «Ланцюг постачання»](release-guide.md#ланцюг-постачання).

1. **Свіжий `main` і чисте дерево:**

   ```powershell
   git switch main
   git pull
   git status --short     # порожньо
   ```

2. **База не спить:** Supabase Dashboard → проєкт активний (якщо ні — **Resume project**). D0 досі зелений:

   ```powershell
   git fetch origin
   git rev-parse origin/main        # <SHA main>
   npm run smoke -- https://<проєкт>.vercel.app <SHA main>
   npm ls next
   ```

   Код 0 і рядок, що починається з «OK —»; на код 1 рядки `::error::` пояснюють, що не так (як у D0). `next` поки може бути 16.4.3 — оновлення прийде в цьому кроці.
3. **Аудит** — промпт [R01 «Аудит готовності до експлуатації (dev, лише читає)»](prompts.md#r01). У слот «Чекліст
   команди» вставте текст розділу [«Рубрика розробника»](../README.md#рубрика-розробника-що-дивимось) з README (або
   посилання, якщо ваш агент може відкривати сторінки): агент додасть кожен її пункт окремим рядком таблиці.
   Розпакований `accounts.txt` перед аудитом приберіть з теки репо: R01 читає все репо. Агент нічого не змінює; його
   таблиця разом з таблицею нижче — ваш план тижня. Збережіть її (наприклад, в описі першого PR).

   | Область аудиту R01 | Крок цієї домашки | Промпт |
   |---|---|---|
   | 1. CI/CD | 1.4 (дії за SHA, назви jobs без змін); ворота й ruleset `solo-main` — як були | R02 |
   | 2. Середовища, змінні й секрети | 2.1, 2.5 (staging, `APP_ENV`) | R03 |
   | 3. Реліз і відкат | 5 (тег `v1.0.0`); відкат і Promote — у runbook, 4.11; прапорці — необов'язково | R13, R11, R19 |
   | 4. Health і smoke | 2.1, 2.2 (`appEnv`, smoke кожного деплою) | R03, R04 |
   | 5. Алерти | 3.3 | R05 |
   | 6. Трекер помилок | 3.5 | R06 |
   | 7. Журнали | 3.6 (`llm.call`) | R07 |
   | 8. Залежності й ланцюг постачання | 1.4–1.6 | R02 |
   | 9. Резервні копії | бонус | R17 |
   | 10. Runbook і postmortem | 4.10, 4.11 | R10, R11 |
   | 11. Вартість і ліміти | трек PM, крок 4; [гайд вартості](cost-guide.md) | R16 |
   | 12. Права агентів | 4.1 (профіль «лише пропонує») | R08 |
4. **PR `chore/supply-chain`** — промпт [R02 «Ланцюг постачання: dependabot.yml, .npmrc, дії за SHA»](prompts.md#r02).
   У слот «шаблони» дайте посилання на набір (блок «Для домашки WS11» під R02): файл Dependabot і рядки для `.npmrc`
   агент бере звідти. Самі — так:

   ```powershell
   curl.exe -fsSL --create-dirs -o .github/dependabot.yml "$B/ops-kit/.github/dependabot.yml"
   ```

   ```bash
   curl -fsSL "$B/ops-kit/npmrc.add" >> .npmrc   # Git Bash: дописати в кінець, не перезаписати
   ```

   У PowerShell рядки з `npmrc.add` найпростіше дописати в `.npmrc` редактором (відкрийте файл набору в браузері й
   скопіюйте) або доручити агенту в R02. **Дописати, а не перезаписати:** у вашому `.npmrc` можуть бути свої рядки.
   Дії GitHub — за повним SHA з коментарем версії; назви jobs у `ci.yml` не змінюються. CI зелений → злиття.
5. **Налаштування безпеки репо** (вебінтерфейс GitHub, Settings → Code security; точні назви перевірте в інтерфейсі):
   - **Dependabot alerts** і **Dependabot security updates** — увімкнути: безпекові оновлення приходять одразу, пауза
     `cooldown` на них не діє;
   - **Push protection** — Enable. Для репо він вимкнений за замовчуванням, навіть якщо GitHub сам сканує секрети;
   - **Code scanning → CodeQL analysis → Set up → Default.**

   Знімок цієї сторінки (без чужих даних) — доказ для D.
6. **`next` ≥ 16.4.5 через PR Dependabot.** Після злиття `dependabot.yml` бот відкриває PR (безпекове оновлення може
   прийти раніше за розклад; версійне — у груповому PR `npm-minor-and-patch`, станом на 17.11 уже з 16.4.6 — теж
   зараховується). Якщо PR немає довше доби — Insights → Dependency graph → Dependabot, перевірте, що бот
   запускався (точну назву перевірте в інтерфейсі), або зробіть власний PR з тим самим оновленням — теж зараховується.
   CI зелений → злиття → smoke проду зелений → `/api/health` показує новий SHA. **PR Dependabot з `supabase` 3.x не
   зливайте:** конфіг набору його ігнорує, але якщо такий PR усе ж прийшов — закрийте з коментарем «тримаємо 2.x до
   demo day» (чому — у [release-guide](release-guide.md#ланцюг-постачання)).

**Доказ (у файл здачі):** PR `chore/supply-chain` з `dependabot.yml`, рядками `.npmrc` і діями за SHA; PR Dependabot (чи
ваш) з `next` ≥ 16.4.5 і зеленим CI; знімок налаштувань push protection і CodeQL або посилання на перший прогін CodeQL;
`/api/health` проду з `"db":"ok"` і SHA `main`; зелений прогін smoke на `main`; `accounts.zip` на SHA і ролі тестових
акаунтів (лише адреси `*@example.test`); версія `next` з `npm ls next`.

## 2. Staging і smoke кожного деплою (~1,5 год) — трек A

Навіщо: PM приймає реліз не на проді, а на генеральній репетиції — staging. На безкоштовному Vercel це гілка
`staging` зі своєю адресою і своєю змінною середовища. Smoke тепер перевіряє кожен деплой, зокрема staging, за адресою
саме цього деплою. Як влаштовано й чого staging **не** дає (окремої бази) — у
[release-guide, «Staging на Vercel Hobby»](release-guide.md#staging-на-vercel-hobby) і
[«Спільна база»](release-guide.md#спільна-база-правила-staging).

**Порядок важливий:** подія Vercel `repository_dispatch` запускає workflow **лише з файлу на `main`**. Тому спершу
зливаємо новий smoke і `/api/health` у `main`, а вже потім створюємо `staging`.

1. **`/api/health` показує середовище** — промпт [R03 «Staging: гілка, змінна для гілки, доступ PM»](prompts.md#r03).
   На staging `VERCEL_ENV` теж `preview`, тому відрізнити staging допомагає ваша змінна `APP_ENV`, яку health додає
   окремим полем. Поля D0 (`ok`, `sha`, `env`, `db`, `reason`) не змінюються. PR → злиття.
2. **Smoke кожного деплою** — промпт [R04 «Smoke кожного деплою з обходом захисту»](prompts.md#r04). Файли набору можна
   завантажити самим, тоді агент працює з `git diff`:

   ```powershell
   foreach ($f in ".github/workflows/smoke.yml", "scripts/smoke.mjs") {
     curl.exe -fsSL --create-dirs -o $f "$B/ops-kit/$f"
   }
   ```

   ```bash
   for f in .github/workflows/smoke.yml scripts/smoke.mjs; do curl -fsSL --create-dirs -o "$f" "$B/ops-kit/$f"; done
   ```

   Перевірте в diff: прод-job поводиться як раніше (`PROD_URL`, SHA `main`, щоденний розклад — він ще й «будильник» для
   бази), новий job бере адресу з `client_payload.url`. PR → злиття.
3. **Обхід захисту для автоматики** (Protection Bypass for Automation — перепустка для робота):
   - Vercel → ваш проєкт → Settings → Deployment Protection → Protection Bypass for Automation → створити секрет (точні
     назви перевірте в інтерфейсі). Там же подивіться, чи ввімкнено Vercel Authentication: у WS6 `bootstrap.md` радив
     її вимкнути. Якщо вмикаєте — режим **Standard Protection** (прод-домени лишаються відкритими: D0 і перевірка курсу
     читають прод без входу), не All Deployments.
   - Значення — у GitHub Secrets, з терміналу (CLI спитає значення, в історію команд воно не потрапить):

     ```powershell
     gh secret set VERCEL_AUTOMATION_BYPASS_SECRET
     ```

     Або Settings → Secrets and variables → Actions → New repository secret. Значення — більше ніде.
4. **Гілка `staging` від свіжого `main`:**

   ```powershell
   git switch main
   git pull
   git switch -c staging
   git push -u origin staging
   ```

5. **Змінна лише для гілки** — Vercel → Settings → Environment Variables → нова змінна `APP_ENV` = `staging`,
   середовище **лише Preview**, гілка **`staging`** (назви полів перевірте в інтерфейсі). Або з Vercel CLI ≥ 64.7.0:
   `vercel env add APP_ENV --environment preview --git-branch staging` (значення CLI спитає). Змінні діють **лише на
   нові деплої**: якщо деплой `staging` уже зібрався без неї — Deployments → останній деплой `staging` → Redeploy.
6. **Адреса staging.** Кожна гілка вже має стабільну адресу виду `<проєкт>-git-staging-<scope>.vercel.app`. Справжню
   скопіюйте з Vercel → Deployments (фільтр за гілкою `staging`): довгі назви обрізаються, не збирайте її вручну.
   Власний домен необов'язковий; як його прив'язати до гілки — у [release-guide](release-guide.md#staging-на-vercel-hobby).
   Відкрийте `<staging>/api/health`: має бути `"env":"preview"`, `"appEnv":"staging"`, `"db":"ok"`. На проді — без
   `"staging"`.
7. **Зелений smoke на деплой staging:** Actions → smoke → прогін, запущений подією `repository_dispatch` для деплою
   `staging`. У журналі видно адресу staging, а значення секрету — ні. Червоний через стіну входу Vercel — секрет не
   задано чи задано з помилкою в назві.
8. **Доступ PM до staging.** На Hobby три варіанти: запит доступу (один зовнішній користувач на акаунт Hobby), спільне
   посилання (одне на акаунт) або вимкнений захист preview. Порівняння — у
   [release-guide, «Доступ PM до staging»](release-guide.md#доступ-pm-до-staging-на-hobby). Окремого перемикача «захист
   вимкнено лише для гілки `staging`» серед можливостей Hobby ми не знайшли — якщо побачите його в інтерфейсі, запишіть.
   Оберіть один варіант, напишіть PM у чат команди адресу staging і що робити, а обраний варіант — у runbook (крок 4).
   Спільне посилання містить токен доступу: у публічних файлах — лише адреса без параметрів після «?».
9. **Як staging отримує зміни:** лише з `main`, без окремої розробки — PR `main → staging` або так:

   ```powershell
   git fetch origin
   git switch staging
   git merge --ff-only origin/main
   git push
   ```

   `--ff-only` відмовить, якщо в `staging` є коміти, яких немає в `main`, — так і має бути.
10. **Вхід на staging.** Staging ходить у ту саму базу Supabase, що й прод: лише тестові акаунти з `accounts.zip`,
    жодних руйнівних дій. Якщо після входу чи запрошення вас перекидає на адресу проду — у Supabase → Authentication →
    URL Configuration додайте адресу staging до Redirect URLs (точні назви перевірте в інтерфейсі).

**Доказ (у файл здачі):** адреса staging і гілка `staging`; `<staging>/api/health` з `"appEnv":"staging"`; PR з
`appEnv` і PR зі smoke кожного деплою; як зміни з `main` потрапили в `staging` (PR чи коміт злиття); зелений прогін smoke на деплой `staging` (посилання на прогін); обраний спосіб доступу PM (запишете в
runbook на кроці 4).

## 3. Сигнали: алерт, трекер помилок, `llm.call` (~1,5–2 год) — трек B

Навіщо: про збій першою має дізнатися людина з команди, а не клієнт. Журнали Vercel на Hobby живуть годину, тож те,
що не відправили назовні, о 9-й ранку вже не існує. Драбина сигналів і чому саме ці три — у
[гайді сигналів](signals-guide.md).

1. **Бот і група Telegram** (≈10 хв) — за [гайдом сигналів, «Бот і група»](signals-guide.md#бот-і-група-10-хв) і
   [«Chat id без витоку токена»](signals-guide.md#chat-id-без-витоку-токена). У групі — люди команди, зокрема PM:
   алерт, якого ніхто не отримує, не зараховуємо. Чужий канал алерту теж підходить, якщо туди дивиться людина.
2. **Секрети в GitHub** (значення CLI спитає інтерактивно):

   ```powershell
   gh secret set TELEGRAM_BOT_TOKEN
   gh secret set TELEGRAM_CHAT_ID
   ```

3. **Крок алерту** — промпт [R05 «Алерт людині з червоного smoke»](prompts.md#r05). У наборі крок уже є в обох jobs;
   R05 звіряє його з чеклістом і доповнює, якщо ваш `smoke.yml` власний.
4. **Один навмисно червоний прогін.** Найпростіше — червоний прогін інцидент-дрілу (крок 4): той самий прогін
   доводить і алерт (B), і сигнал дрілу (C). Хочете перевірити алерт раніше — без поломки продукту і без зміни
   `PROD_URL`: Actions → smoke → Run workflow, у полі `url` — `https://example.invalid` (так підказує опис поля в
   `smoke.yml` набору). Job для деплою почервоніє, крок алерту надішле повідомлення. Інші способи — у
   [гайді сигналів, «Доказ»](signals-guide.md#доказ-один-навмисно-червоний-прогін).
   Перед тестом напишіть у групу «тест алерту», щоб ніхто не злякався. Знімок повідомлення — із замазаними chat id,
   токеном, іменами й аватарками.
5. **Трекер помилок** — промпт [R06 «Трекер помилок (Sentry або onRequestError)»](prompts.md#r06). Оберіть шлях:
   - **Sentry** (безкоштовний план Developer, 1 користувач, алерти лише e-mail): у новій гілці
     `npx @sentry/wizard@latest -i nextjs` запускаєте ви, далі R06 перевіряє diff. `SENTRY_AUTH_TOKEN` — лише у Vercel
     Environment Variables; збір входів і виходів моделі вимкнено. Кроки й пастки — у
     [гайді сигналів, «Шлях 1»](signals-guide.md#шлях-1-sentry-безкоштовний-план-developer).
   - **Власний `onRequestError`** без нового акаунта: файл набору → `src/instrumentation.ts`, повідомлення в ту саму
     групу Telegram. `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID` — ще й у Vercel Environment Variables (Production і
     Preview), без `NEXT_PUBLIC_`.

     ```powershell
     curl.exe -fsSL --create-dirs -o src/instrumentation.ts "$B/ops-kit/src/instrumentation.ts.example"
     ```

   Обидва шляхи зараховуємо однаково. **Навмисна помилка — на staging, не на проді:** тестовий маршрут з R06 під
   роллю адміністратора → подія з маршрутом і стеком → знімок без e-mail, cookie й тексту користувача → тестовий
   маршрут прибрати окремим PR або лишити закритим роллю.
6. **Журнал `llm.call`** — промпт [R07 «Журнал llm.call без тексту користувача + тест»](prompts.md#r07):

   ```powershell
   foreach ($f in "src/lib/log.ts", "src/lib/ai/llm-log.ts", "tests/llm-log.test.ts") {
     curl.exe -fsSL --create-dirs -o $f "$B/ops-kit/$f"
   }
   ```

   ```bash
   for f in src/lib/log.ts src/lib/ai/llm-log.ts tests/llm-log.test.ts; do curl -fsSL --create-dirs -o "$f" "$B/ops-kit/$f"; done
   ```

   `llm-log.ts` кладіть поруч з вашою AI-функцією WS10, якщо вона не в `src/lib/ai/`. Один рядок JSON на виклик моделі:
   модель, затримка, токени, стан (`ok / needs_info / refused / unavailable`), fallback, версія промпту, id запиту.
   **Тексту користувача, промпту й відповіді моделі немає** — і тест з маркером це доводить. `npm test` зелений без
   ключа. Після злиття й оновлення `staging` один виклик AI-функції на staging дає рядок `llm.call` у Vercel → Logs
   (фільтр за гілкою `staging`) — це один запит з вашого денного ліміту моделі.

**Доказ (у файл здачі):** `smoke.yml` з кроком алерту на SHA; червоний прогін (посилання) і знімок повідомлення без
секретів; трекер: файли на SHA (`instrumentation.ts`, для Sentry — конфіг без токена) і знімок події з маршрутом і
стеком з preview чи staging; PR, яким тестовий маршрут прибрано чи закрито; `src/lib/ai/llm-log.ts` (чи ваш шлях) і
`tests/llm-log.test.ts` на SHA; зелений прогін CI з цим тестом.

## 4. Інцидент-дріл, розбір, postmortem і runbook (~1,5–2 год) — трек C

Навіщо: інцидент — це процедура, а не паніка. Ви один раз проходите її на staging, коли нічого не горить, і
лишаєте в репо все, щоб її повторив будь-хто: runbook, postmortem, нову перевірку. Цикл, варіанти поломки, ролі й
серйозність — у [гайді інциденту](incident-guide.md). Правило дрілу: **лише staging, без міграцій і без бази**.

**До поломки** (журнали Vercel на Hobby живуть годину — налаштовувати посеред дрілу пізно):

1. **Профіль «лише пропонує»** — промпт [R08 «Профіль «лише пропонує» (.claude/settings.json, MCP)»](prompts.md#r08).
   Зразки — `materials/ops-kit/.claude/settings.incident.json` і `mcp.json.example`; як їх поєднати з вашими
   `.claude/settings.json` і `.mcp.json` — у [README набору](../materials/ops-kit/README.md). Рубрика дивиться на
   правила в `.claude/settings.json`; заборони запису нічого не ламають і в щоденній роботі. PR → злиття.
2. **MCP Vercel** (вхід через OAuth, токенів у файлах немає). Якщо сервера `vercel` ще немає у вашому `.mcp.json`
   після кроку 1 — додайте його в проєкт:

   ```powershell
   claude mcp add --scope project --transport http vercel https://mcp.vercel.com
   ```

   Далі в Claude Code — `/mcp` → вхід. Звірте назви інструментів у `/mcp` з `deny` у `.claude/settings.json` (набір
   інструментів сервера змінюється, а префікс `mcp__vercel__` — це ім'я, яке ви дали серверу). Перевірка профілю:
   попросіть агента показати значення будь-якої змінної середовища — має бути відмова. Supabase MCP (`read_only=true`,
   `project_ref`) у шаблоні вже є; для дрілу зі змінною середовища він зазвичай не потрібен.
3. **Норма:** останній прогін smoke на `staging` — зелений. Відкрийте issue «Інцидент-дріл: <коротко>» і запишіть
   **до поломки**: що зламаєте, який сигнал має спрацювати і через скільки. Інцидент, знайдений очима, рубрика не
   зараховує.

**Дріл** — варіант A з [гайду інциденту, «Дріл»](incident-guide.md#дріл-як-зламати-безпечно): хибне значення змінної
лише для гілки `staging`. Час записуйте в одному поясі (журнали Vercel — в UTC) і вкажіть, у якому.

4. **Зламати (T0).** Vercel → Settings → Environment Variables → змінна Supabase з префіксом `NEXT_PUBLIC_` для
   **Preview, гілка `staging`** з хибним значенням (не інший справжній ключ — наприклад, змініть один символ). Ключі в
   Supabase **не чіпайте**: це зламало б прод. → Deployments → останній деплой `staging` → Redeploy (змінні
   `NEXT_PUBLIC_` вбудовуються під час збірки). T0 — коли деплой став Ready.
5. **Сигнал (T1).** Smoke деплою staging червоний (`/api/health` → 503) → повідомлення в Telegram. Запишіть час
   повідомлення. Чекали довше 10 хвилин, а сигналу немає — це вже знахідка для postmortem.
6. **Зберегти докази — у першу годину.** В issue дрілу: посилання на червоний прогін, id чи адреса деплою staging,
   відповідь `<staging>/api/health`, рядки журналу з помилкою (без даних користувачів і секретів), знімок алерту.
7. **Розбір агентом** — нова сесія в корені репо. Якщо в репо є `.claude/settings.incident.json` (профіль дрілу
   окремим файлом, як у наборі), запускайте командою з `materials/ops-kit/README.md`, розділ «Профіль «лише
   пропонує» (C)», крок 3:

   ```powershell
   claude --settings .claude/settings.incident.json --mcp-config .mcp.incident.json --strict-mcp-config --permission-mode plan
   ```

   Сервери MCP у `.mcp.json`, а не в `.mcp.incident.json`, — приберіть `--mcp-config` і `--strict-mcp-config`. Лише
   якщо всі правила дрілу вже в `.claude/settings.json`, досить `claude --permission-mode plan`.

   Далі — промпт [R09 «Розбір інциденту агентом (лише пропонує; докази; «що НЕ є причиною»)»](prompts.md#r09); слоти —
   з блоку «Для домашки WS11» під ним (навчальний дріл, staging, MCP Vercel, workflow `smoke`). Агент читає
   деплої, журнали й прогін і **пропонує** причину й виправлення; спроба запису закінчується відмовою — так і має
   бути. Крок 0 промпту — статус-сторінки провайдерів; інструмента для них у профілі немає, тож вставте в розмову їхній стан для свого регіону (адреси —
   у [гайді інциденту](incident-guide.md#спершу-перевір-провайдера); у дрілі там, найімовірніше, усе зелене — це
   теж відповідь). Назви змінних гілки staging агент не читає сам: на кроці 3 промпту вставте в розмову їхній список з Vercel →
   Settings → Environment Variables — лише назви, без значень. Якщо вхід у MCP не вдався — план Б з `vercel logs` у
   [гайді інциденту](incident-guide.md#без-mcp-vercel-logs).
8. **Стенограма — дослівно.** Експорт розмови (`/export` у Claude Code або копія з терміналу) →
   `docs/incidents/<YYYY-MM-DD>-<slug>-rca.md` із заголовком за `materials/ops-kit/docs/incidents/rca-transcript.template.md`:
   дата, модель, версія Claude Code (`claude --version`), профіль і режим, що агент міг і чого не міг. Перед комітом
   перегляньте файл: значень секретів, chat id і e-mail (крім `*@example.test`) немає. Потрапило значення — спершу
   ротація секрету, потім заміна лише значення на `[ВИДАЛЕНО]`, як описано в
   [гайді](incident-guide.md#стенограма--дослівно). Переказ своїми словами не зараховуємо.
9. **Виправити (T2) — робите ви, не агент.** Прибрати хибне перевизначення для `staging` → Redeploy → smoke staging
   зелений. Це і є «відкат» на staging: Instant Rollback працює лише для прод-деплоїв.
10. **Postmortem** — промпт [R10 «Blameless postmortem»](prompts.md#r10) → `docs/incidents/<YYYY-MM-DD>-<slug>.md` за
    шаблоном набору: хронологія T0–T2 і час від поломки до алерту, вплив мовою користувача, першопричина з доказом на
    кожне твердження, «що НЕ було причиною», що спрацювало й що ні, дії з власником (роль). Жодних імен.
11. **Runbook** — промпт [R11 «Runbook»](prompts.md#r11) → `docs/runbook.md` за шаблоном набору:

    ```powershell
    curl.exe -fsSL --create-dirs -o docs/runbook.md "$B/ops-kit/docs/runbook.template.md"
    ```

    Червоний smoke о 2-й ночі; відкат на проді й Promote; база на паузі; ротація ключа; де журнали і скільки живуть;
    доступ PM до staging (що обрали на кроці 2); чого ніколи не робити. Промпт R11 універсальний, тому **дайте агенту
    разом із ним таблицю «Для домашки WS11» під R11:** Instant Rollback на Hobby лише на попередній прод-деплой і
    Promote після нього; база на паузі → `/api/health` 503, `reason` `paused` → Resume project; журнали Vercel Hobby
    — 1 год, Supabase Free — 1 доба; ключі для ротації; `supabase migration down`, `db reset --linked` і
    `npx supabase@latest` у «ніколи». Саме ці розділи перевіряють рубрика C і PM.
12. **Дія з postmortem → перевірка в CI (T3)** — промпт [R12 «Дія з postmortem → перевірка в CI»](prompts.md#r12).
    Наприклад, `/api/health` називає змінну, якої бракує чи яка хибна (лише назву), а smoke це показує. Перевірка
    червоніє на зламаному стані й зеленіє на виправленому. PR з посиланням на postmortem, у postmortem — посилання на
    PR.
13. Postmortem, runbook і стенограму — PR у `main`. Issue дрілу закрийте з посиланням на postmortem.
14. **Розбір PM.** PM у день 5 лишає у вашому PR коментар-розбір: вплив мовою користувача, доказ на кожне
    твердження, без пошуку винних, власник дії, «червоний smoke о 2-й ночі» і «база на паузі» в runbook. Дайте
    PM посилання на PR, відповідайте на кожне зауваження (виправлення чи аргумент у треді) — як на знахідки
    рецензента.

**Відкат на проді й Promote — знання для runbook, а не вправа.** Instant Rollback на Hobby повертає лише попередній
прод-деплой і вимикає автоматичне просування: наступне злиття в `main` на прод **не потрапить**, доки не зробите
Promote (Deployments → деплой → Promote, Manage на сторінці відкату чи `vercel promote <id або URL>`). База й змінні
середовища не відкочуються, а прод-smoke червоний, доки прод ≠ `main`. Подробиці — у
[release-guide](release-guide.md#відкат-на-vercel-hobby-і-promote). Хочете один раз пройти це руками — необов'язково і
без балів: лише коли ніхто не тестує прод, попередній прод-деплой має бути робочим, попередьте групу алертів (smoke
почервоніє), і **одразу після відкату — Promote** останнього деплою `main`, поки `/api/health` знову не покаже SHA
`main`, а smoke не стане зеленим. Без Promote прод так і лишиться на старому деплої.

**Необов'язково, без балів: аварійний вимикач.** Відкат повертає всю попередню версію; аварійний вимикач (kill
switch) зупиняє лише одну функцію, наприклад AI-помічник, без нового деплою. Чим він відрізняється від відкату,
канарки й blue-green і що з цього доступно на Hobby — у [стратегіях викочування](release-strategies.md); промпт —
[R19](prompts.md#r19). Робіть його окремим PR після основного треку, не між прийманням PM і тегом і не як частину
дрілу (дріл — без міграцій).

**Доказ (у файл здачі):** issue дрілу з передбаченим сигналом і доказами; червоний прогін smoke staging з часом;
`.claude/settings.json` з правилами deny на SHA; стенограма `docs/incidents/…-rca.md` на SHA; postmortem
`docs/incidents/<YYYY-MM-DD>-<slug>.md` на SHA; `docs/runbook.md` на SHA; PR з новою перевіркою і зелений прогін CI; виправлення людиною (PR чи коміт); коментар
PM і ваша відповідь — або «не надходило».

## 5. Реліз-кандидат, приймання PM і тег `v1.0.0` (~20 хв + виправлення) — трек A

Навіщо: тег `v1.0.0` — печатка «цю версію прийнято». Тому порядок такий: реліз-кандидат на staging → PM приймає →
тег. Подробиці — у [release-guide, «Реліз v1.0.0»](release-guide.md#реліз-v100).

1. **Нотатки релізу** — промпт [R13 «Реліз v1.0.0: release.yml і нотатки»](prompts.md#r13):

   ```powershell
   curl.exe -fsSL --create-dirs -o .github/release.yml "$B/ops-kit/.github/release.yml"
   ```

   PR → злиття. Мітки на ключові PR зрізів 1–4 поставте самі (вебінтерфейс PR → Labels), інакше категорії будуть
   порожні.
2. **Реліз-кандидат.** Оновіть `staging` з `main` (крок 2.9) → smoke staging зелений → у чат команди: «реліз-кандидат
   на staging: <staging>». Бажано до кінця дня 4.
3. **Приймання PM.** PM проходить ключовий сценарій demo day на staging під тестовими акаунтами і підписує коментарем
   `Приймання релізу (@<pm>, <дата>): staging <URL>, сценарій ✅ / ❌ крок N → #M` — у вашому PR чи issue (домовтеся
   де). На ❌ PM відкриває issue «Відхилення від вимог»: виправлення — PR у `main` з `Fixes #N` → оновити `staging` → в
   issue «Виправлено: <PR>» → PM перевіряє повторно.
4. **Між прийманням і тегом нічого не зливайте в `main`** (і PR Dependabot теж): інакше тег, staging і прод
   показуватимуть різний код.
5. **Тег і реліз** на коміті `main`, який зараз на проді:

   ```powershell
   git switch main
   git pull
   gh release create v1.0.0 --target main --generate-notes --title "v1.0.0"
   git fetch --tags
   git rev-list -n 1 v1.0.0       # SHA тегу
   curl.exe -s https://<проєкт>.vercel.app/api/health
   ```

   SHA тегу = `sha` у відповіді `/api/health` проду. Або у вебінтерфейсі: Releases → Draft a new release → тег
   `v1.0.0`, target `main` → Generate release notes → Publish (точні назви перевірте в інтерфейсі). Чернетку нотаток
   з R13 можна дописати в опис релізу.
6. **PM не встигає приймати** — за пасивність PM балів не знімаємо. У день 6 поставте тег і напишіть у файлі здачі:
   «приймання PM не отримано: запит <дата>, <посилання на повідомлення чи коментар>».

**Доказ (у файл здачі):** реліз `v1.0.0` (посилання на сторінку релізу) з нотатками за категоріями; коментар PM
«Приймання релізу» (посилання) або рядок «приймання PM не отримано: …»; `/api/health` проду з SHA тегу.

## 6. Здача (~10 хв)

[`submissions/README.md`](../submissions/README.md): PR з `submissions/<team-slug>/<github-login>.md`, заголовок
`WS11: Ім'я Прізвище`, `gh pr create --web` (без `--fill`), окремим коментарем `@coderabbitai review`. SHA — коміт `main`
вашого репо (`git fetch origin` → `git rev-parse origin/main`). Посилання на файли — на SHA (`…/blob/<SHA>/…`), на
прогони — `…/actions/runs/N`, знімки — файлами у вашому репо (наприклад, `docs/ops/<що-на-знімку>.png`, з замазаними токеном, chat id і
секретами), бо канал алерту,
трекер помилок і Vercel ми не відкриваємо.

Перед здачею — самоперевірка без агента:

```powershell
# має бути порожньо (рядки-заглушки на кшталт sb_secret_... сюди не потрапляють)
git grep -n -i -E "[0-9]{8,10}:AA[A-Za-z0-9_-]{30,}|sb_secret_[A-Za-z0-9_-]{20,}|x-vercel-protection-bypass: [A-Za-z0-9]{16,}"
git status --short   # порожньо
```

Знайшли значення секрету в історії git — секрет уже публічний: спершу замініть його (новий токен, старий видалити), потім
прибирайте з файлів.

## Бонус (+10) — одне з двох

Необов'язково. Основний трек — пріоритет. Що зараховуємо — у [README](../README.md#рубрика-розробника-що-дивимось),
розділ «Бонус».

| Варіант | Що зробити | Бюджет | Промпт |
|---|---|---|---|
| **Зашифрована копія бази й відновлення** | `materials/ops-kit/bonus/backup.yml` → `.github/workflows/backup.yml`: вручну й за розкладом, закріплена версія Supabase CLI, дамп одразу шифрується, артефакт — лише зашифрований, короткий строк зберігання. `BACKUP_PASSPHRASE` і `SUPABASE_DB_URL` — секрети середовища `production`. Тренування відновлення за `bonus/restore-drill.md` з порівнянням кількості рядків; розділ «Відновлення» в runbook | ~2–3 год | [R17](prompts.md#r17) |

рядків і розділ «Відновлення» в runbook; для асистента — issue з чернеткою після навмисно червоного smoke, ліміти й
вартість.
