# Набір PM: операційні вимоги, повідомлення клієнту, demo day, вартість

## Що це

Чотири шаблони документів, які PM кладе у своє репо вимог `<pm>/<team-slug>-spec` і заповнює про свій продукт. Кожен
шаблон — markdown з таблицями, підказками в коментарях `<!-- … -->` і рядками з позначкою **«приклад — замініть»**.

| Шаблон | Куди покласти у репо вимог | Трек | Промпт для AI-чату |
|---|---|---|---|
| [`operations.template.md`](operations.template.md) | `docs/operations.md` (або issue «Операційні вимоги») | A (30) | [R14](../../docs/prompts.md#r14) |
| [`incident-message.template.md`](incident-message.template.md) | `docs/incident-message.md` | B (10 з 40) | [R15](../../docs/prompts.md#r15) |
| [`demo-day.template.md`](demo-day.template.md) | `docs/demo-day.md` | C | [R16](../../docs/prompts.md#r16) |
| [`cost-note.template.md`](cost-note.template.md) | `docs/cost-note.md` | C | [R16](../../docs/prompts.md#r16) |

Приймання релізу на staging і розбір postmortem і runbook (решта треку B) шаблону не мають: це коментарі в PR і
issues розробників за форматом з [README домашки](../../README.md#рубрика-pm-що-дивимось) і
[walkthrough-pm](../../docs/walkthrough-pm.md).

## Навіщо

Клієнт питає не «яка у вас архітектура», а «що буде, коли воно ляже, і скільки це коштує». Ці документи відповідають
мовою клієнта:

- **операційні вимоги** — що обіцяємо (SLO), що вважаємо аварією (SEV), скільки даних і часу можна втратити (RPO/RTO),
  хто дізнається першим;
- **повідомлення про інцидент** — як сказати клієнту про збій чесно, без жаргону й без пошуку винних;
- **чекліст demo day** — щоб показ не зупинився, якщо щось зламається;
- **записка про вартість** — що безкоштовне зараз, де межі і скільки коштує справжній продукт.

## Короткий словник

| Термін | Що це | Побутова аналогія |
|---|---|---|
| **SLO** (ціль рівня сервісу) | Обіцянка, яку можна перевірити числом за період | Норма: «100 м за 15 с», а не «бігати швидко» |
| **SLI** (індикатор) | Що саме міряємо для SLO | Секундомір і лінія фінішу |
| **Бюджет помилок** | Скільки збоїв дозволяє SLO | Ліміт пропусків занять |
| **SEV1–3** (серйозність) | Наскільки погано користувачу прямо зараз | Сортування в приймальному відділенні |
| **RPO** | Скільки останніх змін можна втратити | Як часто спрацьовує автозбереження |
| **RTO** | Скільки продукт може не працювати | «Майстер приїде протягом 4 годин» |
| **Алерт** | Автоматичне повідомлення людині про збій | Пожежна сигналізація |
| **Staging** | Окрема копія продукту для перевірки перед випуском | Генеральна репетиція перед прем'єрою |
| **Postmortem** | Розбір інциденту: що сталося, чому, що змінили — без пошуку винних | Розбір польоту після посадки |
| **Runbook** | Покрокова інструкція «що робити, коли…» | Інструкція з евакуації на дверях |
| **План Б** | Що робимо, якщо крок показу зламався | Запасна флешка з презентацією |

## Як підключити (у вебінтерфейсі GitHub)

1. Відкрийте шаблон у цьому репо → кнопка Raw (точну назву перевірте в інтерфейсі) → скопіюйте весь текст.
2. У своєму репо вимог: Add file → Create new file (точні назви перевірте в інтерфейсі), ім'я — з таблиці вище,
   наприклад `docs/operations.md`. Вставте текст.
3. Заповніть поля. Рядки «приклад — замініть» замініть своїми або видаліть. Коментарі-підказки після заповнення
   можна прибрати.
4. Commit changes — просто в `main` вашого репо вимог, як раніше.

**З AI-чатом** (ChatGPT, Claude чи інший) — промпти R14–R16 з [бібліотеки](../../docs/prompts.md). Дайте чату шаблон,
бриф і ваші вимоги; **не давайте** паролів, пароля від `accounts.zip`, адрес Google Таблиць, справжніх імен і назв.
Результат чату — чернетка: кожну цифру звіряйте з [гайдом вартості](../../docs/cost-guide.md), кожен факт про інцидент
— з postmortem розробника.

## Як перевірити

- [ ] У жодному файлі не лишилось рядка з «приклад — замініть»: **скопійований приклад не зараховується**.
- [ ] `docs/operations.md`: 2–3 SLO, у кожного — що міряємо, **де саме** (сервіс, журнал, монітор) і бюджет помилок;
      SEV1–3, по 2 приклади на рівень, хто реагує і як швидко; RPO і RTO з тим, що це означає на безкоштовному
      тарифі; хто отримує алерт (роль); що буде після курсу.
- [ ] `docs/incident-message.md`: факти збігаються з postmortem розробника; немає жаргону, звинувачень і обіцянок,
      яких не виконати.
- [ ] `docs/demo-day.md`: сценарій з часом; на кожну точку відмови — план Б.
- [ ] `docs/cost-note.md`: цифри з датою «станом на»; є «що зламається першим» і «коли переходити на платне».
- [ ] Ніде немає імен людей, назв клієнтів, адрес, сум з договорів, паролів, chat id і адрес Google Таблиць.
- [ ] Посилання на прод і staging — краще без параметрів після «?»; секрету обходу захисту Vercel
      (`x-vercel-protection-bypass`) в адресах немає ніколи.

## Бонус (+5) — без шаблону

Одне з двох, у вашому репо вимог:

- **Нотатки релізу `v1.0.0` для клієнта** (наприклад, `docs/release-notes-v1.0.0.md`): що вміє продукт, мовою
  користувача, по ролях; що відомо як обмеження; без технічних назв комітів і PR.
- **Настільне тренування інциденту (tabletop)** з командою за runbook розробника: ви зачитуєте сценарій («о 2-й ночі
  червоний smoke, база на паузі»), команда вголос проходить кроки runbook. Запишіть сценарій, хто що вирішив, де
  runbook не допоміг і що в ньому змінили (посилання на PR чи коментар).
