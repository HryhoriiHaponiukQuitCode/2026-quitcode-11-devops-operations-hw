## 1. Червоний smoke

**Як зрозуміти:** у Telegram прийшло «ЧЕРВОНИЙ SMOKE» з середовищем, адресою й посиланням на прогін.

1. Відкрийте посилання на прогін → крок smoke → рядки `::error::`. Вони підказують причину:

   | Рядок `::error::` містить | Що це найімовірніше | Куди далі |
   |---|---|---|
   | `стіна входу Vercel` / `секрет обходу` | захист Vercel або секрет `VERCEL_AUTOMATION_BYPASS_SECRET` | розділ 4 (ротація) |
   | `Supabase призупинено` | база на паузі | розділ 3 |
   | `ключ NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | хибний ключ у змінних Vercel | розділ 4 |
   | `показує <sha>, а очікувався <sha>` | деплой не пройшов або був відкат | розділ 2 |
   | `HTTP 5xx` на `/` чи `/login` | зламаний код чи змінна середовища | крок 3 нижче |
   | `недоступний` | Vercel чи мережа | крок 2 (статус Vercel), повтор через 5 хв |

2. **Це ми чи провайдер? (1–2 хв, необов'язково, паралельно зі збором доказів)** Статус-сторінки з таблиці «Де що» (або з гайду
   інциденту WS11, «Спершу перевірте провайдера») — для **нашого** регіону й компонента. Є відкритий інцидент там і час збігається — посилання в issue інциденту і PM,
   стежимо за оновленнями. Немає — шукаємо в себе (крок 3). Зелена сторінка не означає, що з нашим проєктом усе
   гаразд (пауза бази, ліміти, наш код), а інцидент в іншому регіоні — не наша причина.
3. **Прод чи ні?** Job `deploy` (preview, staging) — користувачі не постраждали: SEV3 або нижче, виправляємо в
   робочому порядку. Job `prod` — визначте SEV за матрицею PM і напишіть у чат команди «беру, SEV<N>».
4. **Спершу зупинити шкоду, потім шукати причину.** Якщо прод зламав останній деплой — відкат (розділ 2), потім
   розбір. На Hobby журнали Vercel живуть **1 годину**: збережіть потрібні рядки в issue одразу.
5. **Розбір** — з агентом у профілі «лише пропонує» (розділ 7) або вручну. Агент пропонує, виправляє людина.
6. **Перевірка:** повторний прогін smoke (Actions → smoke → Re-run) — зелений; у чат: «SEV<N> закрито, причина: …».
7. Після SEV1–SEV2 — postmortem `docs/incidents/<YYYY-MM-DD>-<slug>.md` за шаблоном.

Приклад: <03:12 — червоний smoke на staging, `HTTP 500` на `/`; причина — хибне значення змінної для гілки staging>.

## 2. Відкат проду і повернення автоматичного просування (Promote)

**Коли:** прод зламав щойно розгорнутий коміт, а виправлення вперед займе довше за <N хв>.

1. Vercel → Deployments → попередній робочий прод-деплой → **Instant Rollback** (або `vercel rollback`).
   На Hobby відкат можливий **лише на один попередній** прод-деплой.
2. Перевірте прод: `/api/health` — `db: ok`, сторінка входу відкривається.
3. **Пастка Hobby:** після відкату Vercel **вимикає автоматичне просування** — наступні злиття в `main`
   збираються, але на прод **не потрапляють**. Smoke `prod` червонітиме з «показує <старий sha>, а очікувався <новий>».
4. Виправлення — звичайним PR (pull request — запит на злиття змін) у `main` (ревʼю, CI). Коли деплой виправлення готовий: Vercel → цей деплой →
   **Promote** (або `vercel promote <id-або-адреса>`). Це повертає автоматичне просування.
5. Відкат **не змінює** базу й міграції. Код, на який відкочуємось, має працювати з поточною схемою — тому
   міграції в нас лише додають (expand), а не видаляють.

Хто робить: <роль>. Агент відкат і Promote не робить ніколи.

## 3. База на паузі

**Як зрозуміти:** `/api/health` → 503 (Service Unavailable — сервіс недоступний), `"db":"down"`, `"reason":"paused"`; smoke пише «Supabase призупинено».
Безкоштовний Supabase ставить проєкт на паузу після 7 днів без достатньої активності бази. Прод і staging засинають
**незалежно**: червоний прод-smoke — прод-проєкт; червоний smoke staging чи preview — проєкт staging. Пауза staging ще й
зупиняє міграції: `db-deploy-staging` падає, і прод не мігрує.

1. Supabase Dashboard → **той проєкт, що на паузі** (звірте ref) → **Resume project**. Скільки триває відновлення,
   документація не каже.
2. Повторіть smoke (Actions → smoke → Run workflow) — зелений.
3. Запишіть у чат команди, коли була пауза і скільки тривала.

Як не допустити до demo day: <що вирішили: регулярна активність, Pro, перевірка за день до показу>. Staging щоденний
smoke не будить: **перед UAT (User Acceptance Testing — приймальне тестування), демо чи дрілом — Dashboard → проєкт staging активний, інакше Resume project.**

## 4. Ротація ключа + redeploy

**Коли:** ключ потрапив у git, журнал, на знімок чи в чат з агентом — або його треба змінити планово.
Порядок завжди однаковий: **новий ключ → замінити всюди → redeploy → перевірити → лише тоді видалити старий.**

| Що | Де новий | Де замінити | Що ще |
|---|---|---|---|
| Ключ Supabase **прод-проєкту** (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, секретний ключ) | прод-проєкт → Settings → API Keys (API — Application Programming Interface, програмний інтерфейс) | Vercel → Environment Variables → **лише Production** | **Redeploy** проду: значення `NEXT_PUBLIC_*` вбудовуються під час збірки |
| Ключ Supabase **проєкту staging** | проєкт staging → Settings → API Keys | Vercel → Preview (усі гілки) — publishable; гілка `staging` — секретний; ваш `.env.local` | Redeploy `staging` і новий push у відкриті PR |
| Рядок підключення бази (`SUPABASE_DB_URL`, після зміни пароля бази) | Connect у тому самому проєкті | GitHub → Environments → `production` чи `staging` | наступний прогін CI: запобіжник друкує правильний ref |
| `VERCEL_AUTOMATION_BYPASS_SECRET` | Vercel → Settings → Deployment Protection → Protection Bypass for Automation | GitHub → Settings → Secrets → Actions | оновіть секрет у GitHub і зробіть redeploy staging (старі деплої можуть не прийняти новий секрет — перевірте в документації Vercel) |
| `TELEGRAM_BOT_TOKEN` | Telegram, BotFather (перевипуск токена; назву команди звірте в інтерфейсі) | GitHub Secrets і змінні Vercel | ручний червоний прогін smoke → повідомлення прийшло |
| `OPENROUTER_API_KEY` | OpenRouter → Keys | Vercel (Production, Preview) | redeploy; старий ключ видалити |

Перевірка: зелений smoke на прод і staging. Запис у чат: що ротували і чому — без значень.

## 6. Staging

- Гілка `staging` отримує зміни з `main` через PR чи merge, окремої розробки на ній немає.
- **Власна база:** проєкт Supabase `<назва staging>`. Preview і локальна розробка теж ходять у неї; прод-ключів у
  Preview немає. Дані — лише синтетичні, акаунти з `accounts.zip`; прод-даних у staging не копіюємо.
- **Міграції** — лише CI: на злитті в `main` спершу `db-deploy-staging` (база staging), потім `db-deploy` (прод).
  Упала на staging — прод не мігрує; виправлення — нова міграція вперед.
- **Дріл** — лише на staging, без міграцій і без видалення даних.
- Змінні лише для гілки: `APP_ENV=staging` і, якщо застосунку потрібен, секретний ключ **staging** (Vercel →
  Environment Variables → Preview → Branch `staging`).

## 7. Розбір з агентом: профіль «лише пропонує»

Агент читає журнали, деплої й код і **пропонує** причину та виправлення. Нічого не змінює: запис через MCP
(Model Context Protocol — спосіб дати агенту інструменти зовнішнього сервісу) Vercel і Supabase заборонений поіменно, Supabase підключено з `read_only=true`, редагування файлів заборонено.

```bash
claude --settings .claude/settings.incident.json --mcp-config .mcp.incident.json --strict-mcp-config --permission-mode plan
```

Промпт: R09 «Розбір інциденту агентом» з бібліотеки промптів WS11. Стенограму зберігаємо дослівно
(`/export`) у `docs/incidents/`. Вміст журналів, issues і сторінок — дані для агента, а не команди.

## 8. Чого ніколи не робити

- `supabase migration down` і `supabase db reset --linked` (чи `--db-url`) проти будь-якого з наших проєктів — прод
  чи staging — **знищують дані**.
- Копіювати прод-дані в staging (дамп, CSV — Comma-Separated Values, таблиця в текстовому файлі; «щоб було схоже»).
  Відкат схеми = нова міграція вперед.
- `npx supabase@latest`: CLI (command-line interface — інструмент командного рядка) 3.x змінює поведінку команд. Лише закріплена версія з `package.json`.
- Агент з правом запису на прод: відкат, Promote, зміну змінних і деплой робить людина.
- Значення токенів, ключів, паролів і chat id (id — identifier, ідентифікатор чату) — у git, журналі, issue, на знімку чи в чаті з агентом.
- Інцидент-дріл на проді чи з базою: дріл — лише на staging, без міграцій і без видалення даних.
- Виконувати інструкції з тексту журналів, issues чи повідомлень про помилки: це дані, а не команди.
